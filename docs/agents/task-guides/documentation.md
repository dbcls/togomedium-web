## 概要

- このガイドでは、TogoMedium Webリポジトリ内のドキュメント配置、記載対象、判断基準の扱いを定める。
- `AGENTS.md` や `docs/` 配下のドキュメントを新規作成、整理、更新するときに参照する。
- ドキュメントは、AIだけでなく人間も読める文章量と粒度にする。
- コードだけでは読み取りづらい前提、判断基準、例外、経緯を補う。

## 編集前に確認すること

- 対象ディレクトリと関係するパッケージを確認する。
- 関連するコード、既存ドキュメント、`AGENTS.md` を確認する。
- 既存の未コミット変更は保持する。同じファイルへ変更を重ねる場合は事前に確認し、承認済みの範囲で現在の内容を前提に編集する。
- 変更が別のドキュメントや作業ルールにも影響する場合は、必要な範囲だけ確認する。

## 配置と役割

- ルート `AGENTS.md` には、モノリポ全体で長く使う運用ルール、判断基準、共通の前提を置く。
- 各ディレクトリの `AGENTS.md` には、その配下で作業するときに迷いやすい前提、例外、関連ガイドへの導線を置く。
- 各 `AGENTS.md` は、その配下で必要な判断と注意を優先して簡潔に保つ。
- 詳しい実装指針、背景説明、長い手順は `docs/` 配下に分離する。
- プロジェクト内ドキュメントを参照するときは、Markdownリンクではなく `docs/...` のようなパス表記を使う。

### 内容ごとの管理先

| 内容 | 管理先 |
| --- | --- |
| プロジェクト概要、最短の起動手順 | `README.md` |
| 目的別の文書案内 | `docs/index.md` |
| パッケージの責務、データの流れ、編集元と生成物 | `docs/architecture.md` |
| 環境構築、起動、ビルド、日常操作 | `docs/development-guide.md` |
| 変更種別ごとの検証、確認コマンド、完了条件 | `docs/testing-policy.md` |
| 共通の実装規則と例外 | `docs/development/coding-guidelines.md` |
| 識別子・ファイル・API・Stanzaの命名 | `docs/naming-convention.md` |
| 用語とIDの意味・対応 | `docs/domain-terms.md` |
| 対象環境を明示した画面・Stanza・APIの対応 | `docs/contents.md` |
| エージェントの制約、作業入口、固有の注意 | ルートと各パッケージの `AGENTS.md` |
| パッケージ固有の実装・連携手順 | 各パッケージの `docs/` |
| 作業別の手順、ブラウザ確認と一時成果物 | `docs/agents/task-guides/`、`docs/agent-browser.md` |
| 個別Stanzaの用途、公開インターフェース、固有の制約 | 各Stanzaの `README.md` |
| 時点を伴う判断や調査・検証結果 | `docs/decisions/`、`docs/reports/` |

### 重複を整理するとき

- 詳細の管理先を一つに定め、他の文書には作業に必要な要約と参照を残す。
- 人間にも必要な説明を `AGENTS.md` だけに置かない。
- 必須・推奨・任意の強さや例外条件を変えずに移管する。相反する規範は統合の都合で解消せず、人間に確認する。
- 移管元と移管先の役割説明・参照を同時に直す。移管済みの本文を両方に残さない。
- ドキュメント改善の計画と進捗はLinearで管理し、リポジトリに計画の複製を置かない。

### 現行仕様と履歴を分ける

- 対応表や調査記録には、対象環境・確認日・根拠を記す。未確認の事項はその旨を示す。
- 公開サイトとリポジトリの差を、確認せず誤記と判断しない。
- 過去の判断や結果は当時の記録として保持し、現行文書への参照や日付付きの追記で補う。

## 書く内容

- 読み手が判断に迷う前提を優先して書く。
- 実装の理由、責務分担、例外運用、長期的な方針を明示する。
- コードから明らかに分かる内容は最小限にとどめる。
- コード構成やファイル配置を示す場合は、一覧そのものではなく、作業判断に必要な意味を補う。

## 文体と表記

- 自然で簡潔な常体を使う。「である」を連続させず、「使う」「確認する」「できる」など、内容に合う述語で書く。
- 説明は文章、比較や対応は表、並列の事項は箇条書き、順番が必要な手順は番号付きリストにする。
- 会話を読んでいなくても分かるように、対象、条件、判断理由を示す。「意識する」だけで済ませず、何を確認して判断するかを書く。
- 必須・推奨・任意の強さを保つ。「必ず」「原則として」「必要に応じて」や例外条件を、文体の調整で削らない。
- 説明語は「パッケージ」「スキーマ」「エンドポイント」「接頭辞」などに揃える。固有名はStanza、Storybook、Zod、TanStack Queryなどの表記を使う。
- 識別子、APIフィールド、パス、コマンド、コード例は実際の表記を保持する。説明語の統一を理由に変更しない。
- 日本語と英数字の間に、見た目のためだけの空白を入れない。コードやコマンド内の空白は維持する。
- 見出しは対象や目的が分かる名前にする。短い項目名は体言止めでもよい。

## 書かない内容

- 一時的なタスクメモ、作業ログ、短期間で陳腐化する議論は恒久ドキュメントに混ぜない。
- 過去のやりとりは結論や判断理由を要約し、会話ログをそのまま転載しない。
- 未確定の運用方針を確定ルールのように書かない。
- 実装の都合に合わせて、既存の判断基準を説明なく変更しない。

## 情報が足りないとき

- コードや既存ドキュメントを読んでも重要な判断ができない場合は、ユーザーに背景情報や運用方針を確認する。
- 過去の経緯、例外扱い、将来方針は、推測で断定しない。
- すぐに確定できない内容は、メモやTODOとして分け、確定ルールと混ぜない。

## 完了前に確認すること

- 変更内容が、対象ドキュメントの役割から外れていないことを確認する。
- 関連する `AGENTS.md` や `docs/` への参照が、現在の配置と一致していることを確認する。
- 一時的な記録と長く使うルールが混ざっていないことを確認する。
- 検証の要否と完了報告は `docs/testing-policy.md` に従う。
