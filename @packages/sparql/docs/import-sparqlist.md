# 既存SPARQList Markdownの取り込み

この文書では、既存APIのMarkdownを読み、ローカルで実行・比較できるファイル構成へ分割する手順を示す。入力は `.md` ファイル、Markdown本文、または定義ファイルのURLとする。元の検索条件と返却形式を保つことを取り込みの目的とし、改良は別の作業として扱う。

この手順は人間・エージェントが内容を確認して進めるワークフローで、自動取り込みコマンドではない。`pnpm export` は分割済みの定義からMarkdownを作る逆方向の処理で、任意の既存Markdownをそのまま往復変換する機能ではない。

以下のファイルパスは、特記しない限り `@packages/sparql` 基準。コマンドはモノリポのルートから実行する。

## 別セッションでの依頼例

> 添付のSPARQList Markdownを、`@packages/sparql/docs/import-sparqlist.md` に従って取り込んでください。既存APIの比較元としてreferenceに配置し、現在のCLIで再現できるか確認してください。対応外の処理があれば、その内容と必要な対応を整理してください。

URLを渡す場合は添付の代わりにURLを指定する。API名・版・引数などを本文から読み取れる場合は、あらためて入力を求める必要はない。

## 1. 入力と配置先を確認する

1. ルートとパッケージの `AGENTS.md`、パッケージの `README.md` を読む。作業ツリーと、同じAPIを扱う既存フォルダを確認する。
2. Markdownの全文を読む。URLの場合はGitHubの画面だけでなくファイル本文を取得する。APIの実行結果JSONは定義の代わりにはならない。
3. 出典と版を記録する。GitHubならリポジトリ内のパスとコミットを特定し、コミット固定URLを残す。添付・貼り付けで版が不明なら、元ファイル名・受領日・版不明を記録し、後から照合できるよう原文を `source.md` として保持する。原文は生成Markdownで置き換えない。
4. 既存公開APIは `queries/reference/<機能名>/` に配置する。API名が `list_components` ならフォルダ名は `list-components` のようにする。既存フォルダがあれば、重複作成せず版と差分を確認する。

採用予定の改良版を作る依頼なら、referenceを残したまま `queries/apis/` に別の定義を作る。採用を決めていない比較案は `queries/experimental/` に置く。取り込みだけの依頼で、検索条件の修正や新しい返却スキーマへの変更を混ぜない。

### 原文保存ファイルを自動整形から保護する

`source.md` はMarkdown内のコードも含め、受け取った原文を保持する。`check-all` は `format` を実行するため、原文保存後、最初の `format` 実行前に、ルートの `oxfmt.config.ts` の `ignorePatterns` で対象が除外されていることを確認する。

未設定なら `@packages/sparql/queries/reference/**/source.md` を追加する。別の場所に原文を保存する場合も、その原文保存ファイルに限定して除外する。READMEや分割後のコードは通常の整形対象に残す。

保存時と検証後のハッシュ値などで、原文が変わっていないことを確認する。整形で変更された場合は受け取った原文から復元し、除外設定を直してから再確認する。毎回 `format` 後に差分を戻す運用にはしない。

## 2. 実行順と依存関係を読み取る

Markdownのブロックを上から順に読み、引数・参照する変数・保存する変数を整理する。必要な内容を対象READMEの処理説明へ残す。

| 確認対象         | 読み取る内容                                            |
| ---------------- | ------------------------------------------------------- |
| タイトル・説明   | APIの用途。ファイル名やAPI名とは区別する                |
| Parameters       | 名前、既定値、空文字列と未指定の扱い、説明、例          |
| Endpoint         | 接続先、環境変数、途中での切り替え                      |
| SPARQLブロック   | 保存先の変数名、参照する引数・前段の結果、検索条件      |
| 途中のJavaScript | 引数加工、クエリ断片の生成、結果間の受け渡し、外部fetch |
| 最後のブロック   | 返却形式、参照する変数、JSON以外の出力の有無            |

SPARQListはコードブロックを定義順に実行する。バッククォート付きの見出しは、直後の処理結果を保存する変数名を表す。たとえば `count` と `result` が最後のOutputで参照されるだけなら、両クエリ間にデータ依存はない。`result` が前段のJSで作った `media_values` を参照するなら、その前処理も再現する必要がある。

仕様の参照元は [SPARQList Reference Guide](https://github.com/dbcls/sparqlist/blob/main/doc/REFERENCE.md)。解釈が分かれる場合は、対象環境の版と実装も確認する。

## 3. 現在のCLIで扱える範囲を判定する

`api.json` の `inputs` は、整形関数へ渡す名前と `.rq` の対応を表す。任意の処理を順に実行する設定ではない。

ローカルのOutputへ渡るのは `inputs` に指定したクエリ結果だけで、呼び出しも同期処理を前提とする。元のOutputが引数・環境変数・途中のJSの結果を参照する場合や、非同期関数の場合は、対応が必要な依存関係として扱う。

| 元の定義                                                                                   | 取り込み方                                                  |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 同じエンドポイントに送る独立したSELECTと、その結果だけを使う同期的なJSON整形               | `.rq`、`api.json`、`output.mjs` に分割する                  |
| `"{{name}}"` 全体を置換する文字列引数、または非負整数の引数                                | `parameters` で扱える。元の許容値との差を確認する           |
| カンマ区切りの文字列を分割して各要素の前後の空白を取り除き、単一変数のVALUES句へ渡す前処理 | `string-list` で扱える。次項で設定と互換性を確認する        |
| ローカルで試すために具体値を固定したクエリ                                                 | referenceで扱える。固定値と元の変数の対応をREADMEへ記録する |
| 任意の前処理JS、前段の結果を使う次のクエリ、外部fetch                                      | 現在の共通CLIでは処理の連鎖を再現できない                   |
| 複数Endpoint、自由なSPARQL断片の挿入、JSON以外の返却                                       | 現在の標準構成ではそのまま扱えない                          |

対応外の処理を見つけたら、省略したまま「取り込み完了」にしない。出典・ブロック構成・対応外の箇所をREADMEへ残し、共通処理の拡張が必要か、特定の入力だけを固定した比較でよいかを相談する。条件が決まるまでは調査・原文保存までとし、動かない `api.json` を実行可能な定義として登録しない。

たとえば `gmdb_list_media_by_gmids` の `media_values` は、カンマ区切りの引数をSPARQL用の値列へ加工する。通常の文字列置換ではなく、次項の文字列リストとして対応する。新規APIの `export` が生成する `prepared` は所定の引数検証・クエリ選択用で、任意の前処理JSを代行するものではない。

### 文字列リストの前処理

カンマ区切りの文字列を分割して各要素の前後の空白を取り除き、単一変数のVALUES句へ渡す前処理は、`parameters` の `type: "string-list"` で扱う。引数名と置換名が異なる場合は `placeholder` を使う。設定例・入力制約・展開方法は `docs/project-structure.md` の「文字列リスト引数」を参照する。この設定は本パッケージのもので、SPARQList本体の設定ではない。

取り込み時は、元の前処理と次の点を比較する。

- 各要素の前後の空白は取り除かれ、空要素・重複・入力順は保持される。未指定では既定値を使い、空文字列を明示すると空文字列1要素になる。
- 各要素はSPARQL文字列リテラルとしてエスケープされる。原文が引用符やバックスラッシュをエスケープしていない場合、その入力での挙動は変わるため、差をREADMEへ記録する。
- 利用できるのは単一変数のVALUES句の本体全体を置換する形式。引用符内への埋め込み、IRI、複数列のVALUES、自由なSPARQL断片には使わない。

一般の前処理JSやクエリ間の結果受け渡しは、引き続き対応外として判定する。

## 4. ファイルへ分割する

対応できることを確認したら、対象フォルダに次を用意する。

| ファイル          | 内容                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------- |
| `README.md`       | 出典・版、用途、処理の順序、引数、コマンド、出力、元定義との差、検証結果               |
| `.rq`             | 各SPARQLブロック。referenceでは元の変数名に合わせて `count.rq`、`result.rq` などとする |
| `api.json`        | `inputs` と、必要な場合の `parameters`、メタ情報                                       |
| `output.mjs`      | 最後のJSON整形を、単独で動く `json` 関数としてexportする                               |
| `output.test.mjs` | 整形仕様と移植用Outputの単独動作を確認する                                             |
| `validate.mjs`    | 対応する共有Zodスキーマがある場合のローカル検証。任意                                  |

`inputs` のキーは元の変数名を保ち、記載順も元のSPARQLブロックに揃える。複数の処理が同じ変数を上書きする場合など、単純なキーとファイルの対応で表せない構成は前項へ戻る。個別API用のパッケージスクリプトは増やさない。

```json
{
  "inputs": {
    "count": "count.rq",
    "result": "result.rq"
  }
}
```

`.rq` は固定値への置換など記録済みの調整を除き、原文と一致させる。WHEREの不一致、重複、空結果の特殊な扱いなどを見つけても、referenceでは改良しない。READMEに観測した事実と影響を記し、必要なら別区分の改良版で扱う。

Outputは関数のモジュール化以外の変更を最小限にする。`columns`、リンク用オブジェクト、文字列の件数、欠損キー、空配列とnullなど、元の返却形式を維持する。`json` は外部importやモジュール内の別変数に依存させず、必要な補助処理は関数の内側に置く。生のクエリ結果しか返さない定義をAPI形式へ変換する場合も、元の返却形式を確認してから対応する。

Zodを使う場合は `@packages/api` の定義を参照する。参照方法は `docs/project-structure.md` に従う。取り込みのために既存公開APIのスキーマを書き換えたり、`openAPI.ts` に未公開の改良版を登録したりしない。

### 引数とメタ情報

元のParametersにない制約を、referenceの仕様として追加しない。現行CLIの整数引数は非負の安全な整数で、先頭ゼロなども拒否する。元APIと許容値が異なる場合はその差を記録し、必要ならreferenceでは比較用の具体値を固定する。引数の仕組みと制約は `docs/project-structure.md` を参照する。

再生成する場合は、`api.json` に `title`・`description`・各引数の `description` を用意し、必要に応じて `examples` を追加する。使用言語は、モノリポの `docs/agents/task-guides/documentation.md` の「使用言語」に従う。元の説明を翻訳・補足した場合も、出典の原文と区別する。

## 5. 検証して差を記録する

まず対象の整形テストを用意し、通常結果・空結果・欠損・複数値・重複など、そのAPIに関係する条件を確認する。`scripts/output-test-helper.mjs` の `checkStandalone` を使い、移植用Outputもモジュール外で動くことを確認する。可能なら同じ生の結果を元のOutputと分割後のOutputへ渡し、値・型・キー・配列順を比較する。

次の例の `example-api` は作成したフォルダ名へ置き換える。すべてモノリポのルートから実行する。

```sh
# 作成したAPIのローカルテスト
mise exec -- node --test @packages/sparql/queries/reference/example-api/output.test.mjs

# 対象APIを実エンドポイントで実行
mise exec -- pnpm --filter @packages/sparql api queries/reference/example-api

# 保存済みの生の結果で整形だけを確認
mise exec -- pnpm --filter @packages/sparql api queries/reference/example-api --saved

# 共通スクリプトの構文とリポジトリ全体の品質確認
mise exec -- pnpm --filter @packages/sparql check
mise exec -- pnpm check-all
```

### 接続先と検証範囲

問い合わせ前に、元のEndpointとローカルの接続先を確認する。ローカルの接続設定はパッケージの `README.md`、未設定・空の場合の挙動は `docs/project-structure.md` を参照する。

元のMarkdownに環境変数名しかなく実値を確認できない場合も、ローカル接続先での検証は進めてよい。ただし接続先が同じとは推定せず、READMEに元の変数名、実値を確認できなかったこと、実際に問い合わせたURL、検証日・引数を記録する。結論は「指定したローカル接続先で動作確認済み、元環境との同等性は未確認」とする。

接続先の一致を確認できた場合は、同じ引数で元環境との比較を行う。接続先が異なると分かっている場合も、その差を明記してローカルでの検証と元環境の再現を区別する。

対象APIだけを必要な条件で順に実行し、一括実行で全クエリを問い合わせない。引数対応した定義では `--param 名前=値` を使う。固定値で取り込んだものには、その引数を渡さない。`--saved` と `--param` は併用できない。

実データではID・取得項目・重複・欠損・件数を確認し、ページングがある場合は空ページも確認する。公開APIと比較する際は同じ引数・接続先を使い、キャッシュやデータ更新の影響も区別する。件数が同じだけで同等とは判断しない。

READMEには検証日・条件・結果・元定義との差・未確認事項を残す。`results/` は生成物でGit管理外。実行失敗時には前回のファイルが残り得るため、ファイルがあることだけで成功とは判断しない。エンドポイントへ接続できなければ、ローカルテスト済み・実データ未確認と分けて報告する。

### 移植コードのlint警告とエラー

referenceでは元APIの挙動を保つことを優先する。原文から引き継いだ書き方に対するlint警告は、元と同じコードであることと、整形テストで互換性を確認したうえで残してよい。READMEに対象ファイル、ルール名、件数、原文由来であること、保持した理由を記録する。新しく書いた処理の警告までこの例外に含めない。

`pnpm lint` はquiet指定のため、警告の確認にはルートで `mise exec -- pnpm lint:debug` を使う。警告を保持しても品質確認は省略せず、実行したコマンドの終了結果と残る警告を分けて報告する。ignoreコメントやルールの無効化で警告を隠さない。

lint・型チェックのエラーやテスト失敗は、原文由来でも警告と同じ例外にはせず、原因と互換性への影響を示して相談する。未解決の確認項目を成功扱いにしない。元APIにある挙動上の問題は第4節に従って記録し、referenceでの修正と混ぜない。原文保存ファイルは変更せず、改良は別区分で扱う。

## 6. Markdownの再生成が必要な場合

取り込みと再公開は別の作業として扱う。メタ情報とCLIの対応範囲を確認した定義は、次で `dist/sparqlist.md` を生成できる。

```sh
mise exec -- pnpm --filter @packages/sparql export queries/reference/example-api
```

生成時には問い合わせも公開も行わない。元Markdownの説明配置や前処理をそのまま復元するものではなく、現在の分割ファイルから生成する。固定値に置き換えた引数は自動で元に戻らない。生成物のEndpointは `{{SPARQLIST_TOGOMEDIUM_ENDPOINT}}` なので、元の接続先を維持できるか確認する。

生成したMarkdownの引数・検索条件・Outputを元定義と比較する。SPARQListへの登録・実行は別途確認し、ローカルのテストやMarkdown生成だけで公開先でも動作確認済みとは扱わない。公開手順の詳細はパッケージの `README.md` を参照する。

## 完了時に共有すること

- 配置先、出典と版、追加したファイル。
- 保持した挙動と、固定値への置換など元定義との差。
- 実施した検証、未確認事項、対応外の処理が残る場合はその内容。
- コミットや公開の実施有無。取り込み完了と公開完了を区別する。
