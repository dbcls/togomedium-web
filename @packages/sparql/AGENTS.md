# AGENTS.md

## 作業範囲

TogoMediumのクエリ実行・比較・API設計を扱う。公開は `dbcls/togomedium-sparqlist` 側で行い、ローカルの検証を公開済みとは扱わない。

作業前にパッケージのREADMEと対象クエリのREADMEを読む。環境・共通検証・文書規約はルートのAGENTSとガイドに従う。このパッケージ内の相対パスはパッケージ基準とする。

## 分類と正本

- `queries/reference/`: 既存公開APIの比較元。ローカル実行のための引数固定と出典追記は許容する。ロジックの改良は別区分へコピーして行う。
- `queries/experimental/`: 学習、比較、採用未定の試案。
- `queries/apis/`: 採用予定・採用済みの新規API。READMEに採用状態、公開状態、スキーマ連携の有無を記録する。
- referenceを改良するときは元を残し、apisに新しい定義を作る。検討が必要ならexperimentalで試す。
- 入出力スキーマの正本は `@packages/api`。独立して同じZod定義を作らない。既存公開APIのスキーマを試案で置き換えない。

## 実装と検証

クエリごとの設定・整形・テスト・READMEを同じフォルダに置く。共通スクリプトに個別APIの意味を持たせず、個別APIのpackage scriptsは追加しない。

移植元の `.mjs` とNode標準テストは維持する。特に `output.mjs` の `json` はSPARQListで単独実行するため、名前付きfunction宣言を例外として許容し、外部importやモジュール内の別変数に依存させない。Zod検証は `validate.mjs` に分離する。新しい共有型・スキーマはTypeScriptで書く。

クエリ変更時は実エンドポイントで結果を確認する。HTTP成功だけでなく、対象ID、取得項目、重複、欠損、件数、ページングを変更内容に応じて確認する。比較元と件数が同じでも情報が同一とは判断しない。移植だけの場合はクエリ本文の一致も確認する。

整形と共通処理は `pnpm --filter @packages/sparql test`、構文は同パッケージの `check` で確認する。ルートの `pnpm test` でもパッケージのNodeテストを実行する。SPARQLのネットワーク検証は通常のテストから分離する。

## 記録と出力

- 対外向けのタイトル・説明・引数の説明は原則英語で書く。SPARQList用Markdownのメタ情報もこの方針に従う。
- 通常結果は各クエリ内の `results/` に保存し、Git管理外とする。判断の根拠は検証日・条件・比較結果・未確認事項とともにREADMEへ記録する。
- 観測件数は固定仕様と区別する。行数削減を実行速度の改善と同一視しない。
- 新規APIは、明示しない限り `gmdb-meta-list` の共通リストスキーマを前提にしない。
- 各READMEに目的、コマンド、引数の意味と置換、出力、検証結果を記す。引数がなければその旨を示す。
- referenceのファイル名は元APIの名前を維持し、その他は取得内容が分かる名前にする。`result.rq` は共通ルールではない。
